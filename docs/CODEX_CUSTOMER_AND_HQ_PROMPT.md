## 任务 1：顾客端（Telegram Mini App）三处缺口

代码位置：`frontend/src/App.tsx` 的顾客页（订单列表与订单弹窗），后端 `backend/routers/orders.py`（`GET /api/v1/orders`、`GET /api/v1/orders/{code}`）。

### 1.1 已付款订单不再显示「ABA 待支付」
现状：订单弹窗对已确认收款的订单仍显示「ABA 待支付：US$…」，删品后金额也对不上。
要求：
- 付款状态为 `PAID_CONFIRMED`、`PARTIALLY_REFUNDED`、`REFUNDED` 时，**隐藏**「ABA 待支付」，改显示：订单总额、**已支付**（`paid_confirmed_minor`）、**已退款**（已完成退款合计）、**待退款**（有待处理退款时，给顾客的温和说明"店员会尽快处理"）。
- 未付款（`UNPAID`/`REJECTED`/`PROOF_SUBMITTED`）保持原样显示应付与支付引导。
- 后端在 `GET /api/v1/orders/{code}` 增加 `paid_confirmed_minor`、`refunded_done_minor`、`refund_pending_minor`（只含本人订单；金额最小单位整数；币种沿用订单币种）。**不要**暴露退款的内部字段（转账号、操作人等）。
- 删品后：订单总额、已支付、已退款三者在界面上一致（`已支付 − 已退款 − 待退款 = 订单总额`，历史订单无 `paid_confirmed` 时按已有字段合理降级，不显示负数）。

### 1.2 缺货块与按钮去重、缺货未处理时的提示
现状：缺货块里有「取消订单」，底部又有一个「取消订单」；有未处理缺货时仍可点「已付款，发送凭证」。
要求：
- 订单弹窗里**只保留一个**「取消订单」入口（放在底部操作区）；缺货块只放「去掉缺货商品」「更换商品」（若店员提供了替换）两类选择，取消订单走底部按钮，并在缺货块里用一句话提示"也可以取消订单"。
- 存在 `OPEN` 缺货时，「已付款，发送凭证」按钮**禁用**并显示提示"请先处理缺货商品"（三语）；缺货处理完成后恢复。
- 已付款订单只允许"去掉缺货商品"或"取消订单"，不显示更换（与后端规则一致）。

### 1.3 订单列表「待处理缺货」徽标
- `GET /api/v1/orders` 每项增加 `open_issue_count`（只统计 `OPEN`，批量查询，**不得 N+1**，用 SQL 条数用例断言）。
- 顾客订单列表上，`open_issue_count > 0` 的订单显示醒目徽标「待处理缺货」（文字 + 图标，不只靠颜色），点击进入弹窗即可处理。

### 验收（任务 1）
- 后端 HTTP 级测试：他人订单 404；三个新字段数值正确（含部分退款、全额退款、待退款三种）；`open_issue_count` 正确；列表 SQL 条数不随订单数增长。
- 前端测试：已付款订单不渲染「ABA 待支付」；只有一个取消入口；`OPEN` 缺货时凭证按钮禁用；徽标渲染。
- **真实浏览器验证（必须）**：用本地测试 Bot Token 签一份 `initData`，以 `http://127.0.0.1:3001/?tgWebAppData=<url编码的initData>` 打开 Mini App（`TelegramProvider` 会读取该参数；hash 用 `HMAC-SHA256("WebAppData", BOT_TOKEN)` 作密钥对排序后的 `key=value` 串签名，`auth_date` 取当前时间，用户 id 对应种子里的顾客 `telegram_user_id`）。种子里准备：一张未付款订单带未处理缺货、一张已付款（ABA）订单带未处理缺货、一张已付款已删品订单（有待处理 ABA 退款）、一张已完成订单。逐张打开弹窗核对文案与按钮，桌面与 375 窄屏各一遍，并确认 `documentElement.scrollWidth <= clientWidth`；高棉语看一张。贴 DOM 检查记录或截图路径。
- 不要改动订单状态机、退款规则、钱包账务。

## 任务 2：`backend/create_manager.py --hq`

背景：现有脚本只在"系统里没有任何在职经理"时才能运行，且创建的经理 `store_id` 为空（总部）。但现有部署里迁移已把原有员工都归到主店，所以**线上没有总部账号**，而没有总部账号就无法在多店模式下修改共享菜单（见 `docs/DEPLOYMENT_CHECKLIST.md` §6）。

要求：
1. 把脚本核心逻辑重构为可测试的函数（接收数据库会话/引擎参数），命令行只是薄封装。
2. 新增 `--hq`：创建一个 **`store_id` 为空的总部经理**，**允许在已有经理的情况下运行**；不带 `--hq` 时保持原行为（仅首个经理）。
3. 安全约束：
   - 口令只能交互输入（沿用 `getpass`，12–72 字节，两次确认一致），**不得**通过命令行参数或环境变量传入，不得打印。
   - 登录名需符合现有规则（字母数字、点、下划线、连字符，3–64 位）；重名直接报错退出。
   - 创建时写一条 `AuditLog`（`entity_type="staff"`，`action="hq_manager_created"`，`store_id` 为空（总部级）；`actor_staff_id` 非空约束：使用新建账号自身 id，与现有 `initial_manager_created` 写法一致），**details 不含口令**。
   - `--hq` 运行前打印一行醒目的确认提示（将创建可跨店的总部账号），需要输入 `yes` 确认；增加 `--yes` 仅用于自动化测试时跳过确认（不跳过口令校验）。
4. 文档：更新 `docs/DEPLOYMENT_CHECKLIST.md` §6，写明在线上用 `docker compose exec backend python create_manager.py <登录名> --hq` 创建总部账号的步骤、验证方法（登录后能看到门店切换器；多店模式下能改商品）、以及"创建后立即修改口令、保管好"的提醒；`README` 里若有首位店长初始化说明也同步。
5. 测试（HTTP 级或函数级，PostgreSQL 真库）：已有经理时 `--hq` 成功且 `store_id` 为空；不带 `--hq` 在已有经理时拒绝；重名拒绝；弱口令拒绝；审计记录存在且不含口令；新建总部账号能通过 `get_catalog_manager`（多店模式下改目录成功），而门店经理仍 403；总部账号登录后 `/auth/admin/me` 返回 `store_id: null`。
