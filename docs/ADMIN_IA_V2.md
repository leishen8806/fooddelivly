# 管理后台 v2 规划（按最新需求重新评估）

> 本文取代 `ADMIN_IA.md` 中与以下需求冲突的部分；`ADMIN_IA.md` 里的接口契约、通用控件规范、安全验收仍然有效。
> 依据：当前代码（阶段 A 已完成：路由化骨架 + 通用组件）、后台 7 条新需求、已落地的门店隔离与退款财务口径。

**与上一版规划的冲突点（以本次需求为准）**：上一版用右侧**抽屉**做新建/编辑；现在统一改成**二级页面**（列表右上角主按钮 → 独立路由页，带面包屑与返回）。抽屉只保留给"快速查看"类场景，且本期不用。

## 1.5 页面布局硬规则（所有后台页面一致，验收项）

1. **列表页只放列表。** 页面自上而下固定为：页头（标题 + 右上角主按钮「新增 …」）→ 工具栏（搜索、筛选、日期；仅用于**查询列表**）→ 列表/表格 → 分页。**不得出现任何新建/编辑表单**，也不得把表单放在列表前面、上方、侧边或折叠区里。
2. **新建与编辑只存在于二级页面**（独立路由）。上一级页面只提供入口：右上角主按钮（新建）和行内「编辑」（编辑）。
3. 二级页面自上而下：面包屑 → 页标题 → 表单分块 → 底部固定「取消 / 保存」。保存成功回到列表，保留原筛选与页码。
4. 设置页是例外中的规则化：`/admin/settings` 只是分组只读卡片，每张卡一个「编辑」入口进二级编辑页；编辑表单不放在概览页。
5. 「每日报表」里"发送到员工群"是**操作按钮**不是新建表单，可留在页内，但放在报表下方或页头操作区，不得排在数据前面。
6. 现有页面里"表单在列表前"的情况（商品页的分类/商品表单、员工页的新建表单、优惠券页的创建表单、设置页长表单）在对应阶段**全部迁出**，不保留旧布局。

> 自动化验收：为每个列表页写 vitest/DOM 测试，断言页面中除工具栏内的搜索/筛选/日期控件外，没有任何 `<form>` 或表单输入；断言存在「新增」入口且指向二级路由；二级页包含面包屑与保存/取消。

## 3. 订单列表（需求 2、3）

**列**

| 列 | 来源 | 说明 |
|---|---|---|
| 订单号 | `public_code` | 点击进二级详情页 |
| 下单时间 | `created_at` | 门店时区 |
| 下单用户 | `customer.display_name`（Telegram 昵称）+ `@username` | 无昵称时显示用户名，再无则显示 Telegram ID |
| 打开聊天 | `customer.telegram_chat_url` | 见下方说明 |
| 房间号 | `room_number` | |
| 订单金额 | `subtotal_minor` | 商品小计（删品后为调整后金额） |
| 优惠金额 | `coupon_discount_minor` | 0 显示 `—`，不显示 `-$0.00`；有优惠券时下方小字显示券名 |
| 应付金额 | `total_minor` | 小计 − 优惠 + 配送费 + 服务费（悬停显示拆解） |
| 实收金额 | 见下 | |
| 支付 / 状态 | 徽标 | 保留现有 |
| 操作 | 主按钮 + ⋯ | 接单/确认支付/出餐/送达/完成；⋯：取消、报缺货、退款 |

**实收金额口径（默认值，待你确认）**：`实收 = 已确认收款 paid_confirmed_minor − 已完成退款(order_refunds.DONE)`；未确认付款的订单为 0；`REFUNDED` 为 0；有待处理退款的订单在小字提示"待退 $x"。这与财务统计的 ABA/钱包口径一致，不会二次口径分叉。

**打开聊天**：有 `@username` → `https://t.me/<username>`；没有 → `tg://user?id=<id>`（只能在装了 Telegram 的设备打开，浏览器里可能无反应）。因此无用户名时按钮旁加「复制 ID」。

**搜索与筛选（需求 3）**
- 关键字输入框：同时匹配 订单号（前缀/包含）、用户昵称、`@用户名`（不区分大小写；`%` `_` 转义，参数化）。
- 日期：起始日期～结束日期两个日期控件，**含结束日整天**；按门店时区转 UTC 后用 `[开始日 00:00, 结束日+1 00:00)` 查询。只选起始则到今天，只选结束则从最早。起始大于结束时提示。
- 其余：状态 Tab（带计数）、支付状态、支付方式；全部写进 URL；翻页保留筛选。
- 服务端分页（默认 25，上限 100），排序白名单（下单时间、应付金额）。

**接口**：`GET /api/v1/admin/orders/search`（参数 `q`、`from`、`to`、`status[]`、`payment_status`、`payment_method`、`limit`、`offset`、`sort`；返回信封 `{items,total,limit,offset}`，`items` 含 `customer{id,display_name,username,telegram_user_id,telegram_chat_url}`、金额字段、`refund_done_minor`、`refund_pending_minor`、`received_minor`）、`GET /api/v1/admin/orders/counts`、`GET /api/v1/admin/orders/{code}`。旧 `GET /admin/orders` 保留。门店隔离沿用 `store_scope_clause`。

## 4. 商品 / 分类 / 优惠券（需求 4、5）

**商品管理列表**：列 = 图片、名称（当前语言，缺翻译标红徽标）、分类（chips）、价格、规格/加料数、售卖时间摘要、甜度、状态（上架/售罄）、排序、操作（编辑、上下架）。
**筛选**：名称搜索、分类（单选）、状态（全部/上架/售罄）、是否缺翻译、是否带规格。商品量不大，先用**前端过滤**（接口不变）；超过几百条再下沉服务端。
**新增/编辑二级页**（`/admin/products/new`）：分块表单 = 基本信息（三语名称与描述用 `LocalizedInput` 页签、图片、价格 `MoneyInput`、分类多选、排序、甜度、上架）→ 规格与加料 → 售卖时间（后两块沿用现有 `AdminProductRules`，编辑页内展示；新增页保存后跳到编辑页继续配置）。

**分类管理列表**：列 = 名称（三语）、商品数、排序、状态、操作（编辑、启用/停用）。右上角「新增分类」→ 二级页：三语名称、排序、启用。需要接口补**商品数**（`GET /admin/categories` 增加 `product_count`）。
**注意**：目录是全店共用的，多店时仅总部可写（已落地的 `get_catalog_manager`）；两个页面对门店经理只读。

**优惠券**：列表列 = 名称、类型/规则摘要、发放方式、有效期、领取/总量、状态、操作；右上角「新增优惠券」→ 二级页（现有表单搬入）；保存后返回列表。后续可补"已使用数/作废"，本期不做。

## 5. 财务拆分（需求 6）

- 「每日报表」`/admin/finance/daily` = 现有日报（日期、预览、文本、发送到员工群、投递状态）。
- 「财务统计」`/admin/finance/stats` = 现有区间统计（日期范围；ABA 收款、钱包扣款、充值、**现金净流入**、退款、待处理、对账差额等）。
- 两页内容原样搬迁，**不得丢卡片**（阶段 A 曾误删区间面板，已修复）。STAFF 对两页只读，"发送到员工群"仅 MANAGER。

## 6. 设置与员工（需求 7）

**员工权限**
- 列表列：账号、角色、归属门店（总部可见）、Telegram ID、状态、最近登录（新增）、操作（编辑、停用/启用）。右上角「新增员工」。
- 二级页 `/admin/staff/new`：登录名、初始密码（强度提示，12+）、角色、归属门店（仅总部可选）、Telegram ID。
- 二级页 `/admin/staff/:id`：改角色、Telegram ID、**重置密码**（返回一次性临时密码，首次登录强制改密）、停用。不能停用自己、不能降级自己。
- 后端新增：`staff.last_login_at`、`must_change_password`、`POST /admin/staff/{id}/reset-password`（见 ADMIN_IA 附录 A.6）。

**设置**（"创建新的内容"在设置里对应：营业时间段新增、门店新增）
- `/admin/settings` 为**概览页**：按分组显示当前值的只读卡片（营业、收款、通知、区域/自动化），每张卡右上角「编辑」→ 对应二级编辑页。
- 营业：接单开关、营业时间段（可多段，"新增时间段"在编辑页内）、起送、配送费、服务费、未付款超时/提醒、缺货响应超时、缺货退款复核阈值。
- 收款：币种（只读，变更需总部二次确认）、ABA 二维码、支付链接。
- 通知：员工群 ID、群语言、**发送测试消息**。
- 区域：时区。
- 总部另有「门店管理」（新增门店 = 二级页）——依赖门店 CRUD 接口，放在后续阶段。

## 7. 总览图表与用户统计（需求 1）

**图表（零依赖，用内联 SVG 自绘柱/折线/环形；遵循三语、深浅色、可访问性：颜色之外带文字或图案）**

| 图 | 数据 | 说明 |
|---|---|---|
| 订单趋势 | 近 7/30 天每日订单数 + 销售额（双轴或双图） | 不含取消；日期按门店时区 |
| 订单状态分布 | 今日/所选期间各状态数量（环形或横条） | |
| 支付方式占比 | ABA / 钱包 / 混合 | |
| 时段分布 | 24 小时订单数柱状图 | 看高峰，决定备餐 |
| 热销商品 TOP 10 | 按销量 | 来自订单明细快照 |
| 用户趋势 | 每日新增用户 + **日活** 折线 | |

顶部指标卡：今日订单、今日销售额、待接单、待核款、待处理退款、**总用户数、今日新增用户、今日活跃用户**（点击跳转到对应列表）。

**日活定义（默认，待确认）**：当日（门店时区）**打开过 Mini App 的去重用户数**。依据：每次打开都会调用 `/auth/telegram` 登录。采集方式：新增 `customer_daily_activity(customer_id, store_id, activity_date, first_seen_at, last_seen_at, PK(customer_id, activity_date))`，在登录成功时 `INSERT … ON CONFLICT DO UPDATE last_seen_at`（一天一行，写入量 = 活跃用户数，很小）。
- **没有历史数据**：上线前的日活无法还原。迁移时可用「当天有下单」按订单回填一份历史（标注为"下单用户"口径，与"打开用户"口径不混用），或从上线日起显示。
- 因此**采集要在本批改动里最先上线**，让数据尽早积累。
- 「今日用户数」歧义：我按「今日新增注册用户」实现（日报里已有这个口径），并与「今日活跃用户」分开显示，避免混淆。

**接口**：`GET /api/v1/admin/dashboard?days=7|30&store=`，返回 `kpis`、`series`（按日数组）、`status_breakdown`、`payment_breakdown`、`hourly`、`top_products`；一次请求，服务端聚合，门店隔离同订单（总部可 `?store=`）。

## 9. 需要你确认的 3 个口径（我已给出默认值，不阻塞开工）

1. **实收金额** = 已确认收款 − 已完成退款（默认）。若你要的是"订单应付金额"，则直接用应付金额即可，实收列可删。
2. **日活** = 当日打开 Mini App 的去重用户（默认）。若你要"当日有下单的用户"，改为从订单统计，无需采集，但会偏低。
3. **日期过滤时区** = 门店时区（默认），因为日报与财务均按门店时区。

## 10. 风险与注意

- 搜索/排序参数必须白名单和参数化；关键字转义 `%`、`_`。
- 订单列表禁止 N+1：25 行分页的 SQL 条数不随行数增长（用 SQLAlchemy 事件计数断言）。
- 日活写入发生在登录路径上：必须幂等、失败不影响登录（异常吞掉并记日志），并在限流之内。
- 二级页的表单要有未保存提示；保存失败保留输入；三语文案同步；高棉语检查溢出。
- 旧地址与旧接口保留，逐步下线；每个阶段单独提交，附验证记录。
