# 上线当天操作清单（单店上线）

> 配套文档：详细检查项见 [`DEPLOYMENT_CHECKLIST.md`](DEPLOYMENT_CHECKLIST.md)（以下称"清单"，章节号指其中的 §）。本文只规定**当天的顺序、负责人、放行与回滚条件**。
> **本文不会替你操作线上环境。** 每一步由负责人亲自执行或明确授权后再执行；破坏性步骤（迁移、重启、恢复）必须先备份。
> 范围：单店上线，新自动化保持关闭。多店（第二家店）不在本次范围，见清单 §6。

## 0. 角色

| 角色 | 职责 |
|---|---|
| 发布负责人 | 执行部署命令、决定放行/回滚 |
| 业务验收人（店长） | 在 Telegram 里走联调场景、确认群里消息 |
| 值守人 | 上线后 24 小时内看日志、待处理退款、日报 |

## 1. 放行前（T-1 天，全部满足才进入当天）

| # | 检查 | 通过标准 |
|---|---|---|
| 1 | 代码已评审并合并到 `main` | `release/admin-v2` 的 PR 已有人复核通过；`git log origin/main` 含最终提交 |
| 2 | 质量门禁（清单 §9）在**最终提交**上重新跑过 | 后端 PostgreSQL 15 集成测试全过（`RUN_DB_TESTS=1`，无 skipped）；前端 `tsc`/构建/测试/lint 全绿 |
| 3 | 备份演练 | 有一份**能恢复**的 `pg_dump`（至少 `pg_restore --list` 通过，最好恢复到临时库跑一次迁移链） |
| 4 | 线上当前迁移版本已确认 | `alembic current` 为 `k0123456789d`（否则先弄清原因） |
| 5 | 低峰时段 + 值守人就位 | 避开营业高峰和 22:35 日报 |
| 6 | 店员已被告知变化 | 后台地址与菜单变化（清单 §12）、列表页新增要点右上角、群按钮可能短暂无响应 |
| 7 | 回滚路径已演练 | 清单 §8：知道"回滚代码前会因迁移版本更高而起不来"这一点，并已在演练环境试过处理办法 |

**不放行的情形（任一即延期）**：备份不可恢复；迁移在副本库耗时/报错不明；测试出现 skipped 却无解释；店长无法当天实机联调。

## 2. 当天步骤

### T0 备份（清单 §2）
1. `pg_dump -Fc` 导出数据库；打包上传卷（付款凭证、商品图）。
2. 备份文件**拷出 VPS**，记录文件名与大小。
3. 记录当前镜像 ID、当前提交哈希（回滚用）。

### T1 部署（清单 §3）
1. `git pull --ff-only`，`docker compose build backend frontend`，`docker compose up -d`。
2. 盯日志，确认迁移依次出现 `l → m → n → o → p → q`，无报错；`p` 回填耗时记录下来。
3. 放行条件：三个容器 healthy；`alembic current` = `q0123456789j`。
4. **失败即停**：迁移报错、容器反复重启 → 不要手动改库，直接进入 §4 回滚判断。

### T2 即时检查（清单 §4，5 分钟）
- `/health`、`/api/v1/menu`、`/admin` 能登录。
- 三项自动化阈值为 0（不会取消任何订单）；日活回填有数据；`must_change_password` 全为 false。
- 日志无 `ERROR`。

### T3 总部账号（清单 §6，**单店也建议做**，为以后开店留好入口）
1. `docker compose exec backend python create_manager.py <登录名> --hq`（交互输入口令，输入 `yes` 确认）。
2. 用该账号登录后台：顶栏出现门店切换器；立刻**修改口令并妥善保管**。
3. 不要把口令写进聊天、仓库或文档。

### T4 真实 Telegram 联调（清单 §5，业务验收人执行，约 30–40 分钟）
必须实机走完，**自动化测试全部 mock 了 Telegram**：
- 顾客：下单、自助取消、缺货处理（未付款）、已付款删品、查看已付款订单金额显示。
- 员工群：新单卡片、取消后卡片更新、缺货处理结果消息。
- 后台：接单/确认支付/出餐/送达/完成全流程；完成一笔 ABA 人工退款后财务页"现金净流入"变化。
- 员工安全：重置密码 → 强制改密；设置页"发送测试消息"群里真的收到；故意填错群 ID 看到失败原因。
- 打开 Mini App 后当天日活 +1。
- 22:35 日报含退款相关行且无裸 key。

### T5 放行决策
- 全部通过 → 进入 §3 的灰度开启。
- 任一"资金相关"场景异常（金额不符、重复退款、通知发错人）→ 立即按 §4 处理，不要继续开启新功能。

## 3. 灰度开启新自动化（上线后 1–2 天，由店长在「设置 → 营业设置」操作）

按清单 §7 的顺序，**一次只开一项**，各观察至少半天：
1. 缺货退款复核金额（如 5.00）→ 观察大额退款是否进入待批准。
2. 缺货响应超时（如 20 分钟）→ 观察提醒与升级消息。
3. 未付款超时提醒（如 5 分钟）→ 再开未付款超时（如 30 分钟）。**先只开一家门店，确认取消通知与群卡片更新都发出后再继续。**

每天固定做：清空「待处理退款」（经理）、看对账差额是否为 0、看日报是否按时到达。

## 4. 回滚触发条件与做法

| 触发 | 做法 |
|---|---|
| 迁移失败/容器起不来 | 停服务；查日志；**不要手改库**；必要时用 T0 备份恢复（清单 §8，会丢失备份之后的订单，须负责人决定并事后对账钱包） |
| 迁移成功但核心流程不可用（无法下单/无法接单/无法登录） | 优先**回滚代码**（旧镜像；注意旧版启动会因迁移版本更高而失败，按清单 §8 的演练办法处理），数据库保持不动 |
| 资金类异常（重复退款、金额错、钱包余额不一致） | 立即关闭相关自动化阈值（设为 0），冻结相关操作；保留现场（日志、`order_refunds`、`audit_logs`）；不要在线"修数据"，先备份再评估 |
| 仅界面问题 | 不回滚，记录并修复后发补丁 |

回滚后必做：通知店员、保留故障时间段的日志、事后复盘。

## 5. 上线后 24 小时值守清单

- [ ] 每小时看一次后端日志关键字：`ERROR`、`unpaid order expiry failed`、`cancellation notification failed`、`shortage notification failed`、`限流命中`。
- [ ] 订单量与往日同期无明显异常（排除"下不了单"）。
- [ ] 待处理退款每天清零；对账差额为 0。
- [ ] 日报 22:35 按时到达。
- [ ] 数据库与磁盘占用正常。
- [ ] 收集店员/顾客反馈（尤其手机端布局、缺货流程）。
