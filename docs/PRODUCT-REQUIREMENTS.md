## 1. 产品目标

让住客或私域顾客在 Telegram 内浏览菜单、填写房间号并下单；用 ABA KHQR/支付链接付款后，把付款凭证发给 Bot；店长或服务员核验实际到账，再安排备餐和配送。店员通过管理后台管理商品、订单和财务统计。

首版按**单商家、单门店/厨房**设计。顾客下单不要求注册密码，也不收集姓名、地址或手机号；只收取履约所需的房间号。Telegram 用户身份由服务端验证后取得。

## 2. 用户与权限

| 用户 | 能做什么 |
|---|---|
| 顾客 | 浏览可售商品、提交订单、查看本人订单、向 Bot 提交付款截图 |
| 服务员 | 在管理后台和指定 Telegram 群组查看订单摘要、核实实际收款、更新订单状态 |
| 店长 | 服务员权限；管理商品、查看统计、管理员工权限与营业设置 |

顾客不能访问管理功能。截图不构成付款事实；只有获授权员工确认实际到账后，订单才成为“已付款”。每次人工确认都记录操作人和时间。
店长/服务员可在普通浏览器打开 `https://food.workline.ink/admin` 登录；具体账号凭证方式待确认。员工也可在配置好的 Telegram 群组通过 Bot 按钮处理订单。群管理员身份本身不自动获得 Tea Cafe 员工权限。

## 3. 核心流程

1. 顾客从商家 Bot 的 Mini App 菜单入口打开点餐页面，Telegram 身份自动验证，不出现注册/密码登录页；首次登录先选择界面语言并保存到账户。
2. 顾客在商品瀑布流选择商品和甜度（若该商品启用），逐项加入购物车后可继续选购。
3. 顾客进入独立购物车统一调整商品和数量、填写房间号并提交；之前填写的房间号下次自动回填。价格和总额由服务端依据当前商品数据计算。
4. 服务端创建待付款订单，页面显示该订单的 ABA 收款二维码或支付链接、应付金额和订单编号。
5. 顾客付款后点“已付款，发送凭证”，进入与 Bot 的私聊并发送付款截图。Bot 将截图关联到顾客本人最近/指定的待付款订单。
6. Bot 在指定 Telegram 群组发布订单摘要和“接单”按钮；顾客通过 Bot 私聊提交付款截图后，Bot 将该截图作为回复发送到对应群组订单消息下，员工在群内对照订单核验。员工群必须限制为获授权的 Tea Cafe 工作人员。
7. 获授权员工在群组点“接单”。顾客提交付款截图后，员工对照 ABA 实际到账，再点“确认支付”；未核实到账不得确认。
8. 员工在群组依序操作“出餐”→“已配送”→“已完成”；Bot 更新群组订单卡并私聊通知顾客。

## 4. 功能需求

| ID | 优先级 | 需求与验收结果 |
|---|---|---|
| FR-01 Mini App 自动登录 | P0 | 从 Bot Mini App 合法入口打开后，服务端校验 Telegram `initData` 并建立会话；不要求顾客填写账号密码。校验失败或数据过期时拒绝访问并提示重新从 Bot 打开。 |
| FR-02 菜单浏览 | P0 | 以瀑布流展示分类、商品图、名称、描述、价格、规格/加料（如配置）、售罄状态；仅对店长启用了甜度选项的商品显示甜度选择；售罄商品不可加入购物车。 |
| FR-03 购物车与结账 | P0 | 菜单加购不直接下单；独立购物车支持多商品增减数量、删除和继续选购；结账只要求房间号，保存并预填该顾客上次填写的房间号；提交时再次校验商品有效性和价格。 |
| FR-04 下单 | P0 | 创建不可由客户端改写金额的订单，保存商品名称、单价、规格及数量快照；重复提交不会生成重复订单。 |
| FR-05 ABA 收款说明 | P0 | 展示门店配置的 ABA KHQR 图片或经过核准的支付链接、订单号、应付金额和付款指引。静态码需说明顾客如何确认/输入金额；首版不得伪称已自动对账。 |
| FR-06 提交付款凭证 | P0 | Bot 接收图片并关联到该 Telegram 用户拥有的待付款订单；没有待付款订单、身份不匹配或订单已结束时拒绝关联并说明原因。收到后，Bot 将原图作为对应群组订单消息的回复发送，仅供已授权员工查看。 |
| FR-07 人工核验 | P0 | 授权员工能查看订单与凭证，记录“确认到账/未通过”、原因、操作人和时间；仅“确认到账”可将支付状态改为已付款。 |
| FR-08 订单运营 | P0 | 按状态查看/筛选订单，查看房间号、商品、金额、提交时间和凭证；更新备餐、待取/配送、完成状态；取消需填写原因。 |
| FR-09 商品管理 | P0 | 店长可新增/编辑/下架商品、分类、图片、价格、售罄状态，并逐商品选择是否提供甜度选项；下架或配置变更不影响历史订单快照。 |
| FR-10 财务统计 | P0 | 可按日期查看订单数、订单总额、已确认收款、待核验金额、取消订单数；已确认收款只计入支付已确认的订单。 |
| FR-11 Bot 通知与指令 | P0 | 顾客可用 `/start`、`/orders`、`/help`、`/support`；员工通过 Bot 接收新单/新凭证通知，并可打开订单或进入管理后台。 |
| FR-12 操作审计 | P0 | 管理后台与 Telegram 群组中的商品/设置/员工管理、付款确认/拒绝、订单状态变更和取消均记录操作人、操作来源、时间及前后状态；群组操作关联到已授权员工的 Telegram ID。 |
| FR-13 浏览器后台登录 | P0 | 店长/服务员可在普通浏览器访问 `/admin`；未登录时进入后台登录页。顾客 Mini App 的 Telegram `initData` 登录不能代替后台登录。登录凭证形式需确认。 |
| FR-14 群组订单操作 | P0 | Bot 将新订单摘要发至配置群组，并将用户提交的付款截图以 reply 方式附在对应订单下；提供“接单→确认支付→出餐→已配送→已完成”状态按钮。按有效员工身份、群组 ID 和当前状态授权，写入与后台相同的审计记录。 |
| FR-15 Mini App 语言偏好 | P0 | 顾客首次登录必须选择中文、英语或高棉语；保存到顾客账户。后续只允许在“我的”页面修改，Telegram 语言仅用作首次选择的默认值。 |

## 5. 状态定义

订单履约状态与付款状态分开保存，避免把“上传截图”误当成“已付款”。

**订单状态：**`NEW` → `ACCEPTED` → `PREPARING` → `READY` → `DELIVERED` → `COMPLETED`。任意未完成阶段按规则可进入 `CANCELLED`。群组按钮依序映射为：接单=`NEW→ACCEPTED`；确认支付=`ACCEPTED→PREPARING`（并将付款状态改为已确认）；出餐=`PREPARING→READY`；已配送=`READY→DELIVERED`；已完成=`DELIVERED→COMPLETED`。

**付款状态：**`UNPAID`、`PROOF_SUBMITTED`、`REJECTED`、`PAID_CONFIRMED`。退款/部分退款不在 MVP 内；若业务需要，先补齐退款权限、资金对账和审计规则再开发。

**允许的关键转换：**

| 当前 | 操作人 | 目标 | 限制 |
|---|---|---|---|
| `NEW` | 店员/店长（后台或配置群组） | `ACCEPTED` | Bot 回调验证员工账号、群组 ID 和当前状态 |
| `ACCEPTED` + `PROOF_SUBMITTED` | 店员/店长（后台或配置群组） | `PREPARING` + `PAID_CONFIRMED` | 必须核对 ABA 实际到账；拒绝凭证须记录原因，订单仍待付款 |
| `PREPARING` | 店员/店长（后台或配置群组） | `READY` | “出餐”表示餐品已准备好离开厨房 |
| `READY` | 店员/店长（后台或配置群组） | `DELIVERED` | 标记已交付/送达 |
| `DELIVERED` | 店员/店长（后台或配置群组） | `COMPLETED` | 标记该单完成 |
| 未完成订单 | 店长/员工 | `CANCELLED` | 留下取消人和原因；已确认付款不允许直接取消并抹去收款记录 |

## 6. 财务口径

- **订单总额：**按订单创建时间统计所有订单金额；另列取消金额，避免与有效销售混淆。
- **已确认收款：**按确认时间统计 `PAID_CONFIRMED` 的金额；这只是系统记录的人工核验结果，不等于银行 API 自动对账。
- **待核验金额：**已提交凭证但员工尚未确认的订单金额。
- 所有统计支持日期范围；展示门店时区（默认柬埔寨 `Asia/Phnom_Penh`）和币种。
- 币种/小数位由门店配置；不在未确认前固定 USD、KHR 或汇率规则。

## 7. 非功能要求

- 顾客界面以手机为先，遵循 Telegram 主题色与安全区域，适配常见 Telegram 客户端。
- 所有写接口校验 Telegram 登录会话和角色；所有价格在服务端计算；防止重复下单和重复确认。
- Bot token、ABA 凭据不得放进前端或日志；管理后台仅向授权员工开放。
- 订单、商品快照和付款核验审计需定期备份；付款图片不得公开访问。
- 顾客 Mini App、员工后台、Bot 私聊提示和群组订单按钮完整支持简体中文、英语和高棉语；不允许遗漏文案后回退为 key 或混杂默认语言。
- Mini App 首次打开参考 Telegram 用户语言（中文映射 `zh-CN`，高棉语映射 `km`，其余默认 `en`）并要求顾客确认选择；选择保存到账户，后续只可在 Mini App“我的”修改。后台员工语言独立设置。订单通知沿用下单时顾客语言，员工群组消息使用门店配置语言。
- 商品名称/描述由店长分别维护中文、英语和高棉语版本；未填写某个翻译时以英语作为明确的商品内容回退，并在后台标出缺失语言，不影响操作界面语言。
- 高棉语界面需使用支持 Khmer Unicode shaping 的字体栈，并验收组合符号、行高、按钮宽度、换行与 Android/iOS Telegram 显示。

## 8. 首版不做

多商家平台、骑手派单/轨迹、优惠券/积分、会员等级、AI 聊天点餐、自动退款、库存/供应链、自动化财务对账、公开网站下单入口。首版不要求顾客填写房间以外的配送资料。

## 9. 上线前待确认

1. ABA 商户账户能否提供该商户可用的动态 KHQR、支付链接、PayWay API 或回调；静态二维码如何核验订单金额。
2. 后台登录采用用户名密码、邮箱密码，还是其他凭证；首位店长账号如何安全初始化。
3. 试点使用 KHR、USD 还是两者；菜单币种、汇率和小数位。
4. Telegram 订单群组的 chat ID、哪些员工 Telegram ID 有店长/服务员权限；群组操作的按钮文案和通知语言。
5. 房间号格式、营业时间、缺货后的取消/替换规则；未确认的税费、服务费、配送费不显示、不计入订单。

## 10. 验收演练

使用真实 Telegram 测试账号走完：Mini App 自动登录 → 加购 → 填房间号 → 创建订单 → ABA 收款 → 私聊提交凭证 → 群组/后台接单并核款 → 群组依序出餐、已配送、已完成 → 顾客收到状态通知 → 后台统计核对。另验普通浏览器后台登录、无权限群员不能操作、错误群组 callback 被拒绝、并发点击不会重复转换，以及伪造/过期 `initData`、他人订单凭证、重复提交、售罄和未核款订单不能备餐等边界。

## 多语言文案基线

首版界面语言为简体中文（`zh-CN`）、英语（`en`）和高棉语（`km`）。完整顾客、后台、Bot、状态、支付安全提示和错误提示译文见 [`locales.json`](ui/locales.json)；该文件采用相同 key 集合，新增界面文案必须一次补齐三种语言。代码、API 字段、订单状态常量和 Telegram 命令保持稳定标识，不翻译。
