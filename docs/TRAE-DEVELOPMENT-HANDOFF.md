### 2. 产品范围和必须遵守的业务规则

- 产品：Tea Cafe，单商家、单门店/厨房的 Telegram 私域点餐 MVP。
- 顾客从 Telegram Bot 的 Mini App 入口打开 `https://food.workline.ink/`。Mini App 自动校验 Telegram 身份，不要求顾客注册密码。
- 员工用普通浏览器打开 `https://food.workline.ink/admin` 登录；员工登录与顾客 Telegram 登录分开。
- 顾客可浏览商品、选规格、加购物车、填写唯一配送字段“房间号”并下单。金额必须由服务端计算，客户端价格不可信。
- 创建订单后展示后台配置的 ABA KHQR 图片或支付链接、订单号、应付金额和指引。没有真实支付接口时明确显示人工付款流程，不得显示虚假的自动支付成功状态，也不得把演示二维码当成可收款二维码。
- 顾客付款后通过 Bot 私聊提交付款图片。图片凭证仅限订单本人和授权员工查看，不发到员工群组。
- 凭证上传不等于收款。只有员工核对 ABA 实际入账后才能确认付款；禁止仅凭截图、OCR、按钮点击或客户端状态自动确认到账。
- 店长/服务员可在后台和配置好的 Telegram 群组操作订单。群组卡片按序操作：`接单 → 确认支付 → 出餐 → 已配送 → 已完成`。群管理员身份不自动获得 Tea Cafe 员工权限。
- 群组和后台必须调用同一套服务端授权与状态机；校验员工身份、群组 ID、当前状态、付款凭证及权限。重复点击、并发回调和重复 webhook 必须安全幂等。
- 订单履约状态与付款状态独立记录；所有付款核验、状态转换、商品修改、员工权限变化和取消均写审计事件。拒绝凭证、取消订单必须记录原因。
- 已确认付款订单不能通过普通取消操作抹掉收款记录；历史订单保存商品名称、单价、规格和数量快照。
- 系统首版不做多商家、骑手轨迹、优惠券、积分、自动退款、自动财务对账或 AI 点餐。

### 3. 多语言要求

- 完整支持简体中文 `zh-CN`、英语 `en`、高棉语 `km`，覆盖 Mini App、管理后台、Bot 私聊消息、群组按钮/状态、表单校验、空状态、加载/失败提示和操作确认。
- 以 `docs/ui/locales.json` 为基础文案目录；实现时可以拆分为工程资源文件，但所有语言必须共享相同 key。新增文案时同时补全三语，不得把 key 暴露给用户或静默回退到另一种语言。
- 首次访问优先采用 Telegram `language_code`，映射到支持的 locale；不支持则用英语。Mini App 和 `/admin` 都提供语言切换并保存偏好。创建订单时保存顾客语言快照，Bot 私聊通知沿用此语言；群组语言由门店配置。
- 店长可以为商品分别填写三种语言名称/描述；缺失时商品内容按明确规则回退到英语，并在后台标示缺失翻译。不能把用户输入、订单备注或商品内容自动翻译后覆盖原文。
- 语言只改变显示，不改变订单金额、币种、状态枚举、API 字段或审计数据。日期/数字按 locale 显示，金额使用币种配置格式化，不进行语言相关的汇率换算。
- 高棉语必须使用支持 Khmer Unicode shaping 的字体栈。检查组合字符、字重、行高、按钮高度、断行和小屏溢出；为窄屏预留比英文更宽的布局。

### 4. 建议技术实现

先调查已有技术栈；如果仓库确实没有应用实现，采用项目技术设计中推荐的简洁方案：

- 前端：TypeScript + React + Vite；顾客 Mini App、员工登录和管理后台同源部署。
- 后端：Python + FastAPI；Telegram Bot 可使用 Aiogram 3，以 webhook 接入同一个业务服务。
- 数据库：PostgreSQL；迁移工具与 ORM 选一种成熟方案并固定版本。金额按最小货币单位整数存储。
- 部署：单体应用 + PostgreSQL + HTTPS 反向代理；Docker Compose 作为可复现部署方式。不要无依据引入微服务、Redis、消息队列或大型通用框架。
- 建议模块边界：认证/授权、菜单与商品、订单/价格快照、付款凭证/人工审核、履约状态、Bot/webhook、统计审计、设置/本地化。
- 目录组织以现有项目习惯为先；如从零开始，保持前后端清晰、依赖少、命名直观。

### 5. 身份、安全与会话

- Mini App 使用 Telegram 官方 `telegram-web-app.js`。只向服务端提交原始 `Telegram.WebApp.initData`；绝不以 `initDataUnsafe`、客户端传来的 Telegram ID 或 username 作为认证依据。
- 后端按 Telegram 规范验证 HMAC、`auth_date` 时效与必要字段，使用常量时间比较；拒绝伪造、过期、缺少用户的 initData。非 Telegram 浏览器访问顾客页面时提示从 Bot 打开，不伪造身份。
- 登录成功后使用服务端会话及 `Secure; HttpOnly; SameSite` Cookie；禁止把长期访问令牌放在 `localStorage`。适当执行 CSRF/Origin 校验、速率限制和会话撤销。
- 后台账号使用独立的员工身份、密码安全哈希和角色授权。首位店长初始化采用一次性受控流程；不能提交默认密码、生产密钥或真实 Bot/ABA 凭据。
- Bot webhook 校验 Telegram secret token；Bot callback 每次重新校验员工授权、订单群组 ID 和当前订单状态。
- 对顾客订单做对象级授权；顾客只能访问自己的订单。付款图片通过授权代理/受限访问提供，禁止公开文件 URL、Bot Token 和敏感凭证日志。
- 所有状态变更由后端事务和唯一/幂等约束保护；价格由后端读取商品并重算。

### 6. 订单状态与付款流程

订单状态固定为：`NEW → ACCEPTED → PREPARING → READY → DELIVERED → COMPLETED`，必要时依规则转入 `CANCELLED`。付款状态独立为 `UNPAID`、`PROOF_SUBMITTED`、`REJECTED`、`PAID_CONFIRMED`。

实现并确保以下门槛：

1. 新订单状态为 `NEW + UNPAID`；Bot 通知员工群组。
2. 员工接单后状态为 `ACCEPTED`。顾客可在 Bot 私聊提交图片并绑定到本人有效订单。
3. 只有订单已接单、有付款凭证、授权员工确认已核对 ABA 实际到账后，才可操作“确认支付”；成功后付款为 `PAID_CONFIRMED`、订单进入 `PREPARING`。
4. 拒绝凭证必须填写原因；付款仍未确认，顾客可重新提交凭证。
5. `PREPARING → READY → DELIVERED → COMPLETED` 必须按序进行，并及时更新后台、群组卡片和顾客通知。
6. 非法顺序、无权限、错误群组、重复点击、并发操作、已取消/已完成订单都返回清楚的本地化反馈且不造成重复副作用。

### 7. 管理后台与顾客功能

必须有可用页面和真实业务 API，不接受只有视觉占位的页面：

- 顾客：菜单/分类/搜索、商品详情/规格、购物车、仅房间号结账、下单、ABA 指引、Bot 凭证提交指引、支付核验状态、订单进度/历史、帮助入口。
- 后台登录：浏览器访问 `/admin`；未登录转入 `/admin/login`；错误密码、停用账号、过期会话均有明确处理。
- 总览：当日新单、待核验、已确认收款、制作中等指标；统计口径与门店时区明确。
- 订单：筛选、搜索、详情、付款图片授权查看、确认/拒绝、履约状态变更、取消及原因。
- 商品：分类、三语名称/描述、图片、价格、规格/加料、上/下架、售罄；编辑商品不改写历史订单快照。
- 财务统计：日期范围、订单量/金额、已人工确认收款、待核验、取消订单；清楚标注人工核验口径、时区与币种。
- 员工/设置：店长可邀请、授权或停用员工；配置员工 Telegram ID、操作群组、群组语言、币种、时区、营业信息及 ABA 二维码/支付链接。
- 服务端校验角色：服务员处理订单和核款；仅店长修改商品、员工和门店设置，按产品文档定义细化权限。

至少提供：Telegram 登录/登出、员工登录/登出、当前身份、菜单、创建/读取订单、Bot webhook、后台商品 CRUD、订单列表/详情/状态操作、付款审核、员工管理、统计和门店设置 API。所有写 API 执行身份/角色/对象级授权、参数校验、事务和审计；创建订单支持幂等键。
