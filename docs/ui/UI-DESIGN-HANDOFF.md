# Tea Cafe UI 交互视觉交接稿

> 产品名称：Tea Cafe · 版本 0.1 · 2026-09-29 · 覆盖范围：当前单商家 Telegram 点餐 MVP。以下 SVG 是静态视觉和交互说明，不是可运行页面，也未连接真实 ABA 支付。

## 视觉语言

- **方向：**沿用 Tea Cafe 标志的石板蓝灰与亮青蓝，营造清楚、可信的本地餐饮服务；顾客侧强调食物与房间交付，后台强调订单状态和人工核款。
- **颜色：**品牌石板蓝灰 `#4C6971`（取自 logo 主背景）、亮青蓝 `#46AAD3`（取自 logo 标志图形）、冷调浅灰白 `#F4F8F9`、浅蓝灰 `#E2F1F5`、正文深蓝灰 `#25383D`；错误/拒绝状态使用珊瑚红 `#C75B4B`。
- **排版：**Mini App 与后台共用无衬线字体栈和 12/18、14/20、16/24、20/28、24/32、28/36、36/44 px 字号/行高阶梯。高棉语使用对应字体回退并保持 1.7 行高；中文优先使用系统中文字体。金额、统计数字和 ID 使用等宽数字对齐。
- **控件与间距：**输入框和下拉框统一 44px 高、按钮最小 44px、主按钮 48px；控件/卡片/重点区域圆角分别为 10/16/20px。间距统一使用 4px 基准阶梯（4、8、12、16、20、24、32、40、48px），键盘聚焦显示青蓝色焦点环。后台通过布局密度体现效率，不缩小字号或触控区域。
- **关键视觉标记：**房间号做成订单卡的醒目“交付标签”；付款核验有独立的青蓝状态，不用绿色“已支付”样式冒充到账。
- **语言：**产品界面支持简体中文、英语和高棉语；静态 SVG 用英语展示屏幕布局，三语完整文案见 [`locales.json`](locales.json)。
- 所有图片里的菜名/金额/订单数据均为示例；ABA 区域明确为不可支付占位，不得用于收款。

## 屏幕清单与交互覆盖

### 多语言交互

- 首次打开按 Telegram `language_code` 选择 `zh-CN`、`km` 或默认 `en`；Mini App 与普通浏览器后台均提供语言切换入口，记住用户选择。
- Mini App 建立订单时记录顾客语言；Bot 私聊中的收款指引、凭证结果和订单状态通知沿用该语言。Telegram 员工群使用门店配置的群组语言，后台员工可各自选择界面语言。
- 三种语言共享 [`locales.json`](locales.json) 中的同一组文案 key。新增页面、弹窗、验证错误、空状态、通知和群组按钮时，三语译文须同时提供；不得将按钮或状态编码翻译后写入 API/数据库。
- 菜品名称和描述属于店家内容，按语言分别编辑；缺失译文时按产品需求显示英语商品内容并在管理端提示。数字、订单号和币种格式使用地区化格式化，金额数值本身不转换。
- 高棉语需正确渲染组合字符；行高、按钮尺寸、文本溢出和窄屏布局按高棉语实机检查。

### 顾客 Mini App（主要画面）

顾客端以固定底部三栏切换 **菜单 / 我的订单 / 我的**，适配 Telegram WebView 底部安全区。菜品加入购物车不提交订单；购物车支持多商品统一填写房间号并下单。成功下单后进入“我的订单”，可查看历史订单、付款核验与配送进度；“我的”显示 Telegram 昵称、订单数、已完成订单数和语言设置。

| ID | 画面 | 主交互 | 关键状态 |
|---|---|---|---|
| C01 | 菜单 | 切分类、搜菜、点商品、按商品配置显示甜度、加购 | 首次加载、空菜单、售罄、网络错误 |
| C02 | 菜品配置 | 对启用了甜度选项的商品先选甜度，再加入购物车 | 未选择甜度时不可加入；未启用甜度的商品不显示选择器 |
| C03 | 购物车 | 改数量、删除、继续点餐、结账 | 空购物车、价格变动需重新确认 |
| C04 | 结账 | 输入唯一必填字段“房间号”、确认下单 | 房间号缺失/格式错误、下单处理中/失败 |
| C05 | 收款说明 | 查看应付金额、ABA KHQR/支付入口、复制订单编号 | 配置缺失、付款超时；二维码不能表示自动到账 |
| C06 | Bot 凭证交接 | 打开指定订单的 Bot 私聊并发送付款图片 | 已发送、图片未发、图片类型不支持、订单不匹配 |
| C07 | 待核验 | 查看凭证收到、等待店员核款 | 待核验、未通过并补交、已确认收款 |
| C08 | 订单进度/历史 | 查看备餐、待取/配送、完成状态和旧订单 | 未接单、备餐中、可取/配送中、完成、取消 |

### Telegram 员工群组操作

订单 Bot 将订单摘要发到配置群组，员工在同一消息卡片上按状态逐步操作：

`新单 → 接单 → 确认支付 → 出餐 → 已配送 → 已完成`

- `接单` 要求当前状态为 `NEW`；`确认支付` 要求已接单、有凭证且员工已核对 ABA 实际入账；之后才能按序推进。
- Bot 收到顾客凭证后，将图片以回复方式附在对应订单卡片下方，并更新订单卡供员工继续操作；配置群只允许授权员工加入。截图展示不代表付款已确认。
- 每次点击由服务端再次校验配置群组 ID、员工授权、付款状态和当前订单状态；多人并发只允许一次有效转换。Telegram 群管理员身份不能代替 Tea Cafe 员工权限。
- 每次操作更新群组订单卡、写入审计记录并私聊顾客状态；非法或重复操作显示当前状态，不重复通知或计数。
- 后台操作日志区分页显示操作人、Telegram ID（若已绑定）、操作来源、时间、订单和状态变化；群组操作来源记录为 Telegram 群组。

## 交互矩阵

| 操作 | 即时反馈 | 状态/数据结果 | 下一画面 |
|---|---|---|---|
| Mini App 打开 | 显示启动/身份校验 | 有效 Telegram `initData` 换取会话；失败拒绝 | C01 或重新打开提示 |
| 加入购物车 | 购物车数量/金额更新 | 仅本地暂存选择，不作为最终价格 | C01/C02/C03 |
| 提交订单 | 按钮防重复点击、显示处理中 | 服务端重算并建立待付款订单和商品快照 | C05 |
| 发送付款凭证 | 打开 Bot 对应订单对话，显示发送说明 | Bot 校验 Telegram 身份和订单所有权，保存图片凭证 | C07 |
| 店员确认到账 | 二次确认订单号/金额，操作完成提示 | 写付款核验审计，状态变为 `PAID_CONFIRMED` | A03/A02/C07/C08 |
| 店员拒绝凭证 | 必须输入原因 | 支付标记拒绝，订单可再次提交凭证 | A03/C07 |
| 商品切换售罄 | 列表即时显示售罄 | 新订单不可下单；旧订单快照不变 | A04/C01 |
| 更新订单履约状态 | 显示状态变更和操作人 | 后端状态机校验并发通知 | A02/C08 |

## 交互与状态覆盖说明

视觉稿覆盖当前规划的顾客入口、下单、房间号、支付说明、Bot 图片凭证、人工核款、拒绝重试、履约追踪，以及店员/店长商品和订单操作。关键状态必须遵守：

1. 凭证已上传 ≠ 已支付；只有员工核对实际 ABA 到账后才可确认。
2. 顾客只可看本人订单；员工只可按授权角色操作，店员不能管理员工权限。
3. 只有已确认付款的订单能进入备餐；未付款/待核验订单不可进入厨房制作队列。
4. 已下单商品/单价以订单快照为准；后台改价不改写历史订单。
5. 取消、拒绝核验、重复点击和服务错误均有明确结果与恢复路径，不用 toast 代替状态更新。

本轮只完成视觉交接稿，没有功能实现或浏览器交互验收；因此不把静态画面称作已验证原型。
